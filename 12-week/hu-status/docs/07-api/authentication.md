# Authentication and Authorization Strategy

> How every request is authenticated and authorized. Decisions: ADR-006
> (token validation in every service and service tokens), ADR-001 §6
> (RS256 tokens issued only by Auth).

---

## Mechanism: JWT (RS256), validated by every service

Every service that receives requests validates the token **by itself**:
the four `-api` services and `synkro-workflow`. The gateway only checks
that a credential is present (ADR-006).

```
Client ──Bearer JWT──> synkro-api-gateway ── no Authorization header? → 401
                              │  (forwards the request unchanged)
                              ▼
                       synkro-<domain>-api / synkro-workflow
                         1. validates the token → 401 if invalid
                         2. checks role or permission → 403 if missing
                         3. runs the use case
```

**Validation rules, identical in Java and Go:**

- Only `RS256` is accepted; `none`, `HS256` and any other algorithm are rejected explicitly, whatever the token header says.
- The signature is verified with the public key of `synkro-auth-api` (`JWT_PUBLIC_KEY` or `JWT_PUBLIC_KEY_FILE`). Only `synkro-auth-api` holds the private key.
- `exp` and `sub` are required; a clock skew of up to 30 seconds is tolerated.
- Identity, roles and permissions come only from the token's claims. Any `X-User-*` header is ignored: a header can be set by anyone, a signature cannot.

**Internal calls** (`synkro-workflow` → domain services, `synkro-worker` →
`synkro-products-api`) do not pass through the gateway, and they are
authenticated the same way: with the caller's **service token**. Network
isolation limits exposure (`05-architecture/deployment.md` §7), but it is
not what makes a request trustworthy.

## Token shape

| Claim | Content | Required |
|---|---|---|
| `sub` | `user_id` (UUID) | Yes |
| `roles` | Array, e.g. `["SALESPERSON"]` | Yes |
| `permissions` | Array of granular permissions (see table below) | Yes |
| `iat` | Issued-at timestamp | Yes |
| `exp` | Expiration timestamp | Yes |
| `jti` | Unique token ID (not evidence of an implemented denylist) | Yes |

**Prohibited in the payload:** passwords, card data, full PII (only
`user_id`) — per `00-governance/security-policy.md`.

**Expiration:** access token 1 hour, refresh token 7 days.
**Algorithm:** RS256 (asymmetric) — every validating service holds the
public key; the private key never leaves `synkro-auth-api`.

## Service tokens

`synkro-workflow` and `synkro-worker` call other services with their own
token, never with a person's (ADR-006).

| Aspect | Value |
|---|---|
| Issued by | `POST /api/v1/auth/service-tokens`, `ADMIN` only |
| `sub` | The service name (`synkro-workflow`, `synkro-worker`) |
| `roles` | `["SERVICE"]` — a token-only role, never assigned to a user |
| `synkro-workflow` permissions | `customers:read`, `stock:reserve`, `stock:release`, `sales:register` |
| `synkro-worker` permissions | `products:read`, `stock-alerts:read`, `stock-alerts:write` |
| Expiry | 30 days; an `ADMIN` issues a new one before it expires and the secret is replaced |
| Retried issuance | The same `Idempotency-Key` returns the token's metadata, never the token; `GET /api/v1/auth/service-tokens/{id}` reads it later (ADR-004 Decision 7) |
| Storage | The `SERVICE_TOKEN` secret of each environment; in `develop`, generated by `synkro-infra`'s development scripts |

## Browser session

- The access token lives **in memory** and is sent as `Authorization: Bearer <token>`; the refresh token lives in `sessionStorage`. No cookie carries a credential, so CORS does not allow credentials.
- The session and the only HTTP client live in `synkro-front`; portals use them and never keep a token of their own. A protected-operation `401` ends the session; login and refresh have the distinct outcomes below.
- The residual risk (a script injected in the page could read the tokens) is mitigated by the 1-hour access token, refresh rotation with reuse detection and the Content Security Policy. An `httpOnly` cookie is a future storage option requiring its own security and contract decision; this documentation does not adopt it.

### Production login ownership

`synkro-auth-portal` owns the credential form at `/login`; the host routes and loads that screen without requiring a session. The portal invokes a host-owned authentication operation with the credentials and receives only the user/session outcome or a normalized error. The host uses its shared client for the public login request, consumes the token pair and owns storage, renewal and session notifications. No portal creates a client, stores tokens or manages refresh timers. Development sign-in is temporary; the historical MVP picker is not production login.

### Renewal policy proposal and decision status

**Status: Accepted [ADR-016](../05-architecture/decisions/records/ADR-016-host-session-renewal-and-operation-recovery.md), dated 2026-10-25.** The explicit project decision formalizes the 60-second margin, one-flight coordination and per-tab recovery lifecycle within the existing Host ownership of ADR-008/011. TD-010 is resolved as a policy decision; PR review/publication and runtime evidence remain separate.

### Host-managed renewal and tab recovery

- **Renewal margin:** 60 seconds before access-token exp, as accepted in ADR-016 and observed in the Host. It exceeds the 10-second client timeout but guarantees no scheduling/network completion bound. The timer is an optimization; protected requests and focus/visibility also check expiration.
- At session start, after successful renewal, before each protected request, and when the document returns to visible or the window regains focus, the host checks expiration. With more than 60 seconds remaining, it proceeds without refresh; otherwise it renews before releasing protected work. Missing access-token memory after reload can be restored through the existing refresh credential. Without a usable refresh credential, require login.
- Reading `exp` only schedules client behavior; it does not authenticate a token. Services still validate signature, expiration and authorization locally (ADR-006).
- One in-flight refresh is shared by all callers in the same host session, including simultaneous timer, focus and request triggers. Login/refresh bypass the protected-request gate, preventing recursion. This coordination does not claim cross-tab synchronization.
- Before transmitting a rotating refresh credential, the Host removes its persisted credential/descriptor so a reload cannot replay an in-flight rotation. On success, the host replaces both credentials, updates the session and schedules the next check. On logout, it clears storage and timers, invalidates the local session generation and releases waiting work as cancelled; late login/refresh responses from an older generation cannot restore it.
- On refresh `401`, clear the session and require login. Do not refresh recursively or replay the protected request after a received `401`; renewal is proactive.
- On network/timeout or refresh service failure, stop the renewal attempt and report unavailability, not invalid credentials. Do not blindly resubmit the same rotating refresh token: the server may have committed rotation before the response was lost. Protected work remains gated; an indeterminate rotation requires a fresh sign-in rather than an automatic refresh loop.
- Without a session, protected routes redirect to `/login`; after successful login, return only to a local route authorized for the user, or the role's default landing route.

### Session identity and operation recovery

The released federated shell/session exposes user(): {sub, role} | null, sessionId(): string | null and subscribe(listener: () => void): () => void. Only the Host generates/restores the cryptographic UUID; it is noncredential metadata, not a JWT, token hash, backend authorization claim or proof of authentication. New login rotates it even for the same person; successful renewal/reload retains it with valid subject-bound metadata. Missing/corrupt/mismatched metadata receives a fresh ID only after successful credential restoration.

Commit the complete user/session snapshot before synchronous notification. Invalidation publishes null user and ID; isolate listener errors and make unsubscribe idempotent. Failed storage writes block authentication persistence, while inaccessible storage must not block in-memory logout. The existing Angular Customers ShellContract v1 remains unchanged.

Sales owns one tab-scoped intent journal keyed by (subject, sessionId), with original idempotency key, canonical UUID/quantity fingerprint, optional sagaId and original 24-hour retry deadline. Persist before POST; storage failure blocks registration. Reload does not automatically POST or poll. Explicit GET observes a known saga; unknown-result retry requires the same request/key before the deadline. Expiry never authorizes another key, deletion of an uncertain operation or stock release. COMPLETED with saleId/COMPENSATED clear local recovery; FAILED retains it for attention. Logout/new login invalidates local references even while Sales is unmounted, without cancelling the backend saga.

No cross-tab coordination exists; cloned tabs, tab closure and deleted storage have no recovery guarantee. The 24-hour local ceiling is not a backend retention SLA. Backend idempotency/retention and evidence-sensitive compensation remain separately owned. See [ADR-016](../05-architecture/decisions/records/ADR-016-host-session-renewal-and-operation-recovery.md) and the [frontend capability contract](../_stacks/frontend.md#session-capabilities-and-sales-recovery).

### Authentication outcomes by operation

| Operation / result | Host and portal behavior |
|---|---|
| Login succeeds | Host consumes the token pair, establishes the session and navigates to the authorized destination. |
| Login `401 UNAUTHORIZED` | Show “Correo o contraseña incorrectos” without revealing whether the email exists; clear the password, create no session, and do not refresh or retry automatically. |
| Login network failure, `5xx` or `429` | Show service unavailability or the rate-limit wait; do not label it a credential error. Respect `Retry-After` where supplied; a new login attempt is explicit. |
| Refresh `401 UNAUTHORIZED` | End the session and require login; no recursive refresh. |
| Protected operation `401` | End the session and return to login; no refresh-and-replay. |
| Protected operation `403` | Show access denied; keep the session, with no refresh, role switching or automatic retry. |

## RBAC — Roles and permissions

| Role | Description | Permissions |
|---|---|---|
| `ADMIN` | Business administrator | Full access: users/roles, customers, products, sales, reports |
| `SALESPERSON` | Sales staff | Manages customers, creates sales, checks stock, views their own sales' reports |
| `INVENTORY` | Inventory staff | Manages products, categories, and stock; no access to customers, sales, or reports |

**Permission model** (per `security-policy.md`):

```
customers:create   customers:read   customers:update   customers:delete
products:read      products:write
sales:create        sales:read
reports:read
users:manage
Service tokens only: stock:reserve   stock:release   sales:register
                     stock-alerts:read   stock-alerts:write
```

**Authorization per resource** (each contract in `07-api/contracts/openapi/` lists the exact operations):

| Resource | `ADMIN` | `SALESPERSON` | `INVENTORY` | Service tokens |
|---|---|---|---|---|
| Register a user | ✅ (ADR-014) | ❌ | ❌ | ❌ |
| Login, refresh | Public | Public | Public | — |
| Logout | ✅ | ✅ | ✅ | — |
| Read a user | ✅ | ❌ | ❌ | — |
| Service tokens: issue and read | ✅ | ❌ | ❌ | — |
| Customers | ✅ | ✅ | ❌ | workflow: read |
| Products and categories: read | ✅ | ✅ | ✅ | worker: read |
| Products, categories, stock adjustments: write | ✅ | ❌ | ✅ | — |
| Stock reservations | ❌ | ❌ | ❌ | workflow only |
| Stock alerts: read | ✅ | ❌ | ✅ | worker |
| Stock alerts: open and resolve | ❌ | ❌ | ❌ | worker only |
| Start a sale (`/api/v1/sagas/register-sale`) | ✅ | ✅ | ❌ | — |
| Register a sale in Sales | ❌ | ❌ | ❌ | workflow only |
| Sales and reports: read | ✅ | ✅ (own sales only) | ❌ | — |

**User registration (ADR-014):** register requires a human ADMIN, including
before an idempotent replay. The authentication adapter validates the JWT;
the use case authorizes the trusted caller. User, idempotency key and success
audit record commit together; no creation succeeds without attribution.
Login, refresh and health remain public. Initial administrator creation has
no HTTP route; see `13-operations/initial-administrator-initialization.md`.

**Note on "own sales only":** `synkro-sales-api` compares `sale.created_by`
with the `sub` of the person's validated token (ADR-002). `created_by` is
set by the saga, which sends the salesperson who started the sale; Sales
accepts it only from a caller holding `sales:register` (ADR-006).

**Where each check happens:** the gateway rejects requests without a
credential; each service authenticates the token and authorizes the
operation in its use case, because only the service knows its own rules.

## Authentication/authorization error responses

Both follow the common error envelope in `07-api/guidelines.md`:

**401 — missing/invalid authentication, wrong login credentials or invalid refresh token**
(the gateway for a missing header on protected routes; Auth for login/refresh rejection; the receiving service for invalid protected credentials). The example below is for a protected operation; browser outcomes are defined above:
```json
{
  "error": "UNAUTHORIZED",
  "message": "Missing or invalid authentication token",
  "traceId": "4f1c2b7e-…"
}
```

**403 — valid token, but its roles or permissions do not allow the operation**
(detected by the service):
```json
{
  "error": "FORBIDDEN",
  "message": "Role INVENTORY is not authorized to create sales",
  "traceId": "4f1c2b7e-…"
}
```

## Refresh token flow

- Stored in `auth_schema.refresh_token` (hash, not plaintext); fields and lifecycle semantics are defined in `06-data/models.md` and `06-data/data-dictionary.md`.
- **Mandatory rotation on every use**: one refresh token = one use;
  `POST /api/v1/auth/refresh` invalidates the used token and issues a new one
- Logout invalidates the submitted usable refresh credential only for the validated owner and returns the same idempotent outcome for absent/foreign values. Local logout completes even if that remote request fails.
- Detected reuse of a known inactive, unexpired refresh row rejects with 401 and revokes that owner's active stored refresh credentials. Unknown/expired values reject without inventing an owner. Rotation and owner-wide revocation serialize so a concurrent replacement cannot escape the completed invalidation.
- A password/role-change trigger does not establish an implemented immediate-revocation path; no new endpoint or mechanism is selected here.

---

**Credential-class boundary — Accepted [ADR-017](../05-architecture/decisions/records/ADR-017-refresh-reuse-and-jwt-revocation-boundaries.md):** refresh-row invalidation is implemented in Auth; issued person JWTs remain locally verifiable until exp under the allowed clock skew, and service JWTs are independent scoped credentials. Local logout/session-ID clearing does not revoke either class. No denylist, introspection, token family, per-user version or new store is adopted. The accepted clarification resolves [TD-011](../15-project-control/technical-backlog.md#td-011--clarify-reuse-detection-and-stateless-jwt-revocation); its authority is the explicit 2026-10-25 project acceptance, not implementation or DOCS-95 closure.
