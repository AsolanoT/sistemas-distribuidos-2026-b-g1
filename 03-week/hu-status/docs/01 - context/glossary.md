# Project Glossary

> **How to use this glossary:** Before using a business or technical term in code, documentation, or discussions, look it up here. If it is not listed, add it together with its definition. This is the official dictionary: if there is any ambiguity, this document takes precedence. Add terms throughout the project, not only at the beginning.

## Business Terms

| Term | Definition | Synonyms | Notes |
|---------|------------|-----------|-------|
| Customer | Individual or legal entity that purchases products from SynkroTech SAS | — | Different from a "system user" |
| Product | Technology item or electronic accessory commercialized by SynkroTech SAS | Item, product reference | — |
| Category | Grouping of products with similar business characteristics | — | E.g., "Laptops", "Peripherals" |
| Stock | Available quantity of a product in inventory | Available inventory | — |
| Sale | Commercial transaction in which a customer purchases one or more products | Transaction | — |
| Sales Detail | Each product line associated with a sale | Sales line item | Includes product, quantity, and unit price |
| Traceability | Ability to track the complete history of an operation (who, when, what was done) | Auditing | Implemented through soft deletion, not physical deletion |
| Sales Report | Aggregated information about sales during a period or about best-selling products | — | Generated by the Sales service |
| System User | SynkroTech SAS employee (administrator, salesperson, or inventory employee) who logs in to operate the system | — | Different from a "customer" |
| Role | Category assigned to a system user that determines which operations they can perform | — | Values: ADMIN, SALESPERSON, INVENTORY |
| MVP | First functional version of the system, with the minimum scope necessary to be useful for the business | Minimum Viable Product | — |
| Soft Deletion | Deactivating a record using the boolean field `active` instead of physically deleting it, preserving traceability | — | Applies to all entities in all services |

## Technical Terms

| Term | Definition | Synonyms | Notes |
|---------|------------|-----------|-------|
| Microservice | Independent software component that implements a specific business domain, with its own data schema and deployment lifecycle | — | The project has 4: Auth, Customers, Products, Sales |
| Bounded Context | Conceptual boundary within which a domain model is consistent | — | See `02-domain/domain-map.md` |
| Hexagonal Architecture | Design pattern (Ports and Adapters) that isolates business logic from external technical details | Ports and Adapters | Mandatory in all 4 microservices |
| Port | Interface that declares what the domain needs or exposes without specifying its implementation | — | Defined in the application layer |
| Adapter | Concrete implementation of a port (input: REST controller; output: repository, HTTP client) | — | — |
| Domain | Pure business entities and rules of a service, without framework dependencies | — | See `02-domain/entities-and-rules.md` |
| Use Case | Specific business operation that orchestrates domain rules | — | E.g., "Create Sale" |
| Schema | Logical subdivision within a single PostgreSQL database, owned by a specific microservice | — | See ADR-001 |
| Domain Event | Relevant business fact that has already occurred, expressed in the past tense | Domain Event | See `02-domain/domain-events.md` |
| REST API | Communication interface between services based on HTTP, using standard methods (GET, POST, PUT, DELETE, PATCH) | — | — |

## Authentication and Security

| Term | Definition | Synonyms | Notes |
|---------|------------|-----------|-------|
| JWT (JSON Web Token) | Digitally signed token that carries user identity, roles, and permissions | — | Signed using RS256 |
| Access Token | Short-lived JWT token used to authorize requests | — | Expires in 1 hour |
| Refresh Token | Longer-lived token used to renew the access token without re-authentication | — | Expires in 7 days, with rotation |
| Claim | Data included in the payload of a JWT | — | E.g., `sub`, `roles`, `exp` |
| RBAC | Role-Based Access Control | — | See `00-governance/security-policy.md` |
| Permission | Specific authorization over a resource or action, associated with one or more roles | — | Format: `resource:action` (e.g., `sales:create`) |

## Methodology and Process

| Term | Definition | Synonyms | Notes |
|---------|------------|-----------|-------|
| ADR (Architecture Decision Record) | Short document that records an architectural decision, its alternatives, and consequences | — | Immutable once accepted; changes require a new ADR |
| User Story (US) | Description of a product feature from a user's perspective, with verifiable acceptance criteria | User Story | Format: "As a [role], I want [action], so that [benefit]" |
| DoR (Definition of Ready) | Checklist that determines when a User Story is ready to begin development | Definition of Ready | See `00-governance/definition-of-ready.md` |
| DoD (Definition of Done) | Checklist that determines when a User Story is truly completed | Definition of Done | See `00-governance/definition-of-done.md` |
